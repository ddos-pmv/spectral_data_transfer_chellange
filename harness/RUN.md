# Запуск бенчмарка на AWS

Две машины `m7i.xlarge`, Ubuntu 24.04, одна подсеть, одна AZ.
У каждой **вторая ENI** (`device-index 1`) — по ней идёт трафик, `ens5` остаётся под SSH.
Security group второй ENI должна пропускать UDP/40001 от самой себя.

Всё ниже выполняется **на обеих машинах**, если не сказано иное.

## 1. Установка

```bash
git clone <репозиторий> && cd <репозиторий>/harness
sudo ./scripts/build.sh
cmake -S . -B build && cmake --build build -j$(nproc)
```

## 2. Параметры ядра

```bash
sudo tee /etc/default/grub.d/99-hft.cfg <<'CFG'
GRUB_CMDLINE_LINUX_DEFAULT="$GRUB_CMDLINE_LINUX_DEFAULT isolcpus=1,2 nohz_full=1,2 rcu_nocbs=1,2 irqaffinity=0 idle=poll processor.max_cstate=1 intel_idle.max_cstate=1 transparent_hugepage=madvise"
CFG
sudo update-grub
sudo grep hft /boot/grub/grub.cfg      # строка должна быть на месте
```

```bash
sudo reboot
```
```bash
grep isolcpus /proc/cmdline
```

## 3. Конфиг

```bash
cp scripts/host.conf.example scripts/host.conf
```

Поправить `DPDK_IFACE` — имя второй ENI из `ip a`, обычно `enp40s0`.
Остальное менять не нужно.

## 4. Настройка машины

```bash
sudo ./scripts/host.sh apply
./scripts/checkenv.sh
```

Повторять **после каждой перезагрузки и после `stop`/`start` инстанса**:
привязка карты и настройки ядер живут только до выключения.

## 5. Адреса

На **приёмной** машине:

```bash
./scripts/nic.sh status
```

Выписать `PEER_MAC` и `PEER_IP` и вписать их в `scripts/host.conf`
на **отправляющей** машине.

## 6. Прогон

Приёмная машина, первой:

```bash
sudo IDLE_MS=60000 COUNT=1000000 ./scripts/rx.sh
```

Отправляющая машина, второй:

```bash
sudo ./scripts/tx.sh
```

`rx.sh` завершается сам, набрав `COUNT` замеров, и печатает распределение
задержки. Логи — в `results/rx-<дата>/`.

## 7. Несколько получателей

Поднять `rx.sh` на каждой приёмной машине, снять с каждой `nic.sh status` и
перечислить их в `scripts/host.conf` одной строкой в формате `MAC@IP:PORT`:

```bash
PEERS="02:00:00:00:00:02@10.0.0.2:40001 02:00:00:00:00:03@10.0.0.3:40001"
```

`PEERS` замещает `PEER_MAC`/`PEER_IP`; `tx.sh` дальше не меняется. Отправитель
остаётся **однопоточным** и раздаёт каждому получателю свою TX-очередь, если
карта их даёт столько (`ethtool -l`, строка `Combined` в «Pre-set maximums»).
Если меньше — получатели делят очередь, и отправитель скажет об этом при
старте строкой `asked for N TX queues, device allows M` — на `.large` очередь
одна, и все получатели делят её.

Что смотреть в статистике отправителя после прогона:

| строка | о чём говорит |
|---|---|
| `dest N (qM) : sent ..., tx_dropped ...` | сколько ушло каждому получателю и сколько он потерял на своей очереди |
| `tx_qN_packets` в xstats | подтверждение со стороны карты, что очереди реально задействованы |
| `avg_burst` | растёт с числом получателей — отправитель дольше проходит круг, кольцо успевает накопить |
| `pps_allowance_exceeded` | упор в квоту ENI. Это потолок веера: на каждое сообщение уходит N пакетов, и лечится он не очередями и не ядрами, а только тем, чтобы пакетов было меньше |

Последняя строка — главная. Репликация на источнике здесь не выбор, а
следствие: VPC не форвардит IP-мультикаст между инстансами, поэтому один пакет
физически не может дойти до N получателей. Таблица назначений при этом написана
так, что одна строка с групповым MAC и адресом из 239/8 — это настоящий
мультикаст-сенд на фабрике, которая его размножает; тогда pps перестаёт зависеть
от числа получателей. Проверять это надо на L2-стенде, не в VPC.

Другой темп: `sudo RATE=500000 ./scripts/tx.sh`

## 7. Точность часов

Задержка считается как разница отметок времени двух машин, поэтому расхождение
их часов входит в результат целиком. Перед серией замеров остановить синхронизацию
на **обеих** машинах:

```bash
sudo systemctl stop chrony
```

Прогнать в обе стороны, поменяв машины ролями. Истинная задержка — `(AB + BA) / 2`,
расхождение часов — `(AB − BA) / 2`, по каждому процентилю отдельно. После замеров:

```bash
sudo systemctl start chrony
```

## Вернуть машину в обычное состояние

```bash
sudo ./scripts/host.sh revert
```

## 8. Настройка под m7i

Всё перечисленное уже стоит по умолчанию — раздел о том, что именно и почему,
чтобы числа можно было воспроизвести и оспорить.

**Large LLQ — главная ручка.** `scripts/lib.sh` передаёт карте devarg
`llq_policy=3`. ENA тогда делает записи TX-очереди по 256 байт вместо 128, и в
запись помещается 224 байта inline-данных. Пакет этого транспорта — 42 байта
Ethernet/IPv4/UDP плюс не более 176 байт кадра, итого **218**, то есть входит
целиком: карта забирает пакет записью в собственную память по MMIO и не ходит
DMA-чтением за телом в память хоста. Этот сэкономленный round-trip и есть
основная причина, по которой хвост здесь низкий, и именно под порог 224 в
`message.h` ужат самый крупный тип сообщения (стакан, 176 байт). Отключается
через `LLQ_POLICY=off` в `host.conf` — сравнить с ним стоит, это чистое
измерение того, чего стоит inline.

**Из этого следует мелкое TX-кольцо.** Записи вдвое крупнее — значит в ту же
память карты их влезает вдвое меньше. `SENDER_TXD=512` (дефолт `--txd` тоже
512); если карта отдаёт меньше, отправитель не стартует и печатает число,
которое надо вписать в `host.conf`. Это сделано отказом, а не тихой подгонкой:
глубина очереди влияет на хвост, и подменять её молча нельзя.

**Очередей — по числу получателей, сколько даст инстанс.** Растёт с размером:
на `.large` очередь одна. Проверять до прогона — `ethtool -l ens5`, строка
`Combined` в разделе «Pre-set maximums», **до** отвязки карты от ядра.

**Гипертрединг.** `m7i.xlarge` = 4 vCPU = 2 физических ядра; два busy-spin
процесса на сиблингах делят L1 и исполнительные блоки. Гасится на остановленном
инстансе через CPU options `ThreadsPerCore=1` — на квоту и цену не влияет.

**Собирать на той же машине, на которой мерите.** Сборка идёт с
`-march=native`: на m7i это Sapphire Rapids с AVX-512, и репликация кадра
компилируется в векторные пересылки постоянной длины. Бинарь, собранный на m7i,
на m8a (AMD Genoa) не запустится — если организаторы возьмут m8a, пересобрать
там же, менять в коде ничего не нужно.
